# 既存 EC への結合

注文と決済は別の状態として管理します。注文 ID、作成時に送った `orderId`、返された `paymentIntentId` の対応をサーバーへ保存してください。

## 注文への反映

| 決済の確認結果 | EC 側の扱い |
|---|---|
| 決済途中の6状態 | 入金待ち・処理中として保持 |
| `settled` | 支払い済みにし、一度だけ商品提供処理を予約 |
| `canceled` / `expired` / `failed` | 未提供なら取消・在庫解放の業務処理 |
| `nonce_conflict` | 保留し、運用担当者が結果を調査 |

Webhook とポーリングが競合しても二重出荷しないように、注文の更新を条件付き更新にし、商品提供のジョブを同じ DB トランザクションで記録します。

## 注文と在庫の期限

EC の在庫保持期限は STBLpay の決済期限とは別です。固定の短時間で「もう成立しない」と判断せず、[操作期限・着金期限](/lifecycle/transitions)と実際の状態を照合してください。

自社注文を閉じた後でも、STBLpay の決済が終端になっていなければ成立する可能性があります。提供できない注文への着金を検出したら、運用担当者に連携します。返金する場合は、加盟店コンソールの決済詳細画面から行います（[返金の提供範囲](/refunds/overview)）。

## 二重クリックと再試行

ブラウザでボタンを無効化し、サーバーは同じ注文の再試行に同じ `orderId` を使います。決済の条件を変える場合や別の試行を始める場合は、既存決済が成立しうるかを先に確認します。

復帰ページの表示では、自社セッションから注文を認可します。決済 ID を知っていることだけで注文内容を返さないでください。
