# 銀行 API と消込：自動化できること、例外として残ること、消込を減らす方法（事実集め）

確認日: 2026-11-10。記事は書かない。各事実は出典を実際に読んで確かめたもの。ベンダーの公表値は「(vendor)」と付ける。

方針（delta-1 と Codex の指摘 1〜15 を反映）: 「銀行 API では自動化できない」「必ず手作業が残る」とは書かない。「銀行 API だけでは、注文や請求との対応が決まらない入金がある」「例外の入金は、決めたルールで処理するか、購入者に連絡して確かめる」の形にする。銀行 API で明細を自動取得し、バーチャル口座・照合ルール・消込システム・入金通知を組み合わせれば、多くの入金を自動で照合できる（自動化できること）を先に、例外を後に書く。

## 1. 銀行 API の制度

- 2017 年の「銀行法等の一部を改正する法律」（平成 29 年法律第 49 号。2017-06-02 公布）。金融庁の法案概要は、電子決済等代行業者に「登録制の導入」、銀行に「オープン API の体制整備に努めること」と「電子決済等代行業者との連携・協働に係る方針の策定・公表」「接続に係る基準の策定・公表」を求めると図示している。（検証：要注意 概要 PDF は「法律案の概要」で法律番号・公布日の記載はない。法律番号「平成29年6月2日法律第49号」・施行日 平成30年6月1日は新日本法規（sn-hoki.co.jp。旧版で「第一法規」と書いたのは誤り）の法令改正情報 https://www.sn-hoki.co.jp/article/pickup_hourei/ph611/ （二次）で確認。「努力義務」は原文「努めること」の言い換え）
  出典: 金融庁「銀行法等の一部を改正する法律案の概要」 https://www.fsa.go.jp/common/diet/193/01/gaiyou.pdf
- 【確認済み】金融庁「アクセスＦＳＡ 第179号」https://www.fsa.go.jp/access/30/179a.html 「平成29年５月26日に銀行法等の一部を改正する法律（平成29年法律第49号）が成立（同年６月２日公布）し、電子決済等代行業者の登録制の導入や、体制整備・安全管理に係る措置を求める等の制度的枠組みが整備」「改正法については、平成30年６月１日に施行」。法律番号・公布日・施行日はこの一次で言える（上の二次出典より優先）。（検証：2026-11-10 オーケストレーター確認）
- 記事での「努力義務」の書き方: 「銀行に、オープン API の体制整備に努めることを求めた」（出典は上の金融庁の法案概要）。「API 公開は義務ではない」とは書かない（努力義務も法的義務の一種、と Codex が指摘）。
- 電代業制度の施行日は 2018-06-01。金融庁の 2020-04-30 の報道発表に「電代業制度の施行（2018年６月１日）」とある。（検証：2026-11-10 確認）
  出典: 金融庁（令和 2 年 4 月 30 日の発表） https://www.fsa.go.jp/news/r1/ginkou/20200430-1/20200430.html
- 同ページ: 「電代業のうち家計簿アプリや会計サービスなどの参照系サービス」は、銀行との契約締結義務が施行から「２年を超えない範囲内で政令で定める日」まで猶予され、政令で猶予期限日を 2020-05-31（法律で認められている範囲内で最も遅い日）とした。内閣府令で 2020-09-30 まで延長されたのは、新型コロナの影響で、銀行と電代業者の双方が 5 月 31 日までに契約締結の意向を示していたのに同日までに間に合わないものに限る（同ページ原文）。（検証：2026-11-10 確認。延長は条件付きであることを追記）
- 参照系（残高・入出金明細の取得）と更新系（振込の指示）の区別: 金融庁の概要図は「支払・送金の指示」と「口座情報の取得等」を分けて描く。GMO あおぞらの仕様書は「参照系」と更新系（振込など）を章で分けている（下記 2）。銀行に求めたのは、オープン API の体制整備に努めること（概要の「体制整備に努めること」）。（検証：2026-11-10 確認。GMO あおぞら仕様書の目次は「参照系-口座」「更新系-振込/振替」「更新系-総合振込」「参照系-振込入金口座」）

## 2. 入出金明細 API で取れる項目

【確認済み・現行版】GMOあおぞらネット銀行「オープンAPI仕様書 法人口座編」Version 1.21.0、Last Modified 2026/9/14、https://gmo-aozora.com/business/api-cooperation/pdf/api-spec-corporate.pdf 。振込入金明細の依頼人名 applicantName は最大 48、EDI 情報 ediInfo は最大 20、仕向金融機関名カナ（最大 30）・仕向支店名カナ（最大 15）もある。（検証：2026-11-10 オーケストレーター確認）

以下の項目の詳細は、個人・個人事業主口座編 Version 1.8.0（Last Modified 2021/7/12、旧版。現行版の内容は上の法人口座編で確認した範囲に限る）を読んだもの。記事の出典には現行の法人口座編を使い、「2021 年の版」とは書かない。

- 入出金明細照会: 取引日(transactionDate)、起算日(valueDate)、入払コード(transactionType、1=入金・2=出金)、取引金額(amount)、摘要内容(remarks、最大 255 文字、該当データがなければ項目なし)、取引後残高(balance)、明細キー(itemKey)。摘要の例は「振込 アオゾラ タロウ」。（検証：2026-11-10 確認。旧版にあった「摘要は電文の情報にとどまる」は仕様書の文言ではなく推論なので外した。仕様書は 2021 年版で現行版は未確認）
- 振込入金明細照会: 取引日、起算日、入払コード（「常に1=入金のみ」）、摘要内容（最大 255 文字）、取引金額、依頼人名(applicantName、最大 48 文字、「半角文字」。例は半角カナ「ｱｵｿﾞﾗｼﾖｳｼﾞ(ｶ」)、仕向金融機関名カナ、仕向支店名カナ、EDI 情報(ediInfo、最大 20 文字)、明細キー。摘要内容・依頼人名・EDI 情報は「該当データがない場合は項目自体を設定しません」。（検証：2026-11-10 確認。入払コードの欄を追記、依頼人名の型は原文「半角文字」に合わせた。仕様書は 2021 年版で現行版は未確認）
- つまり通常口座の振込入金明細で取れる照合の手がかりは、振込に載る依頼人名・EDI 情報（20 桁）・金額・日付、仕向けの銀行と支店など（バーチャル口座の明細は別で、下の補足と Webhook のとおり口座 ID・口座番号が付く）。注文番号を入れる専用の欄はない。EDI 情報に番号を載せてもらう運用はできるが、振り込む人が入れた場合だけ入る（「注文番号を伝えられない」ではなく「専用欄がない」）。摘要の例「振込 ｾｲｷﾕｳｼﾖﾊﾞﾝｺﾞｳ123 アオゾラショウジ（カ」のように EDI 情報と依頼人名が摘要に並ぶ。（検証：2026-11-10 確認。「注文番号の欄がない」は項目一覧からの判断）
- 補足: 同じ仕様書に「参照系-振込入金口座」（振込入金口座_発行・_入金明細照会など）があり、GMO あおぞらは API でバーチャル口座（振込入金口座）も扱える。入金明細には振込入金口座 ID・口座番号・入金金額・振込依頼人名カナが出る。（検証：2026-11-10 確認。個人・個人事業主口座で実際に使えるか、料金は未確認）
  出典: https://gmo-aozora.com/business/service/pdf/api-spec-indivisual.pdf
- 利用条件・料金: 仕様書 PDF からは読み取れなかった。検索結果の要約では「本番接続には接続審査と契約が必要」とあったが、一次で確認できていない。sunabar（開発用の無償環境）のログインページは読めたが条件の記載はなかった。
- 【確認済み】入金通知（Webhook）: GMOあおぞらネット銀行「オープンAPI仕様書 イベント通知編」Version 1.21.0、Last Modified 2026/9/14、https://gmo-aozora.com/business/api-cooperation/pdf/api-spec-webhooks.pdf 。「振込入金口座_入金明細通知」は、振込入金口座（バーチャル口座）への入金明細を、銀行システムから配信先へ POST で知らせる。個人事業主口座・法人口座向けのスコープがある。通知の順序は保証されない。正常応答が確認できないと同じ通知が重複して届くことがある。障害で失われた通知は、振込入金口座の入金明細照会 API で取り直す。（検証：2026-11-10 オーケストレーター確認）
  記事での書き方: バーチャル口座と通知を組み合わせれば、入金をすぐ知って照合できる（自動化できること）。ただし重複や取りこぼしへの備えは要る。旧版の「提供済みと確認できた銀行はなかった」は撤回。他行の提供状況は未確認。
- 三菱 UFJ・みずほ・住信 SBI の明細 API 項目は一次で確認できなかった（下記「確かめられなかったこと」）。

## 3. 全銀 EDI システム（ZEDI）

- 稼働開始: 2018-12-25 午前 8 時。資料に「2018年12月25日午前８時から、『全銀EDIシステム』（愛称：ZEDI（ゼディ））が稼動を開始しました」。（検証：2026-11-10 確認。資料の提出者は金融庁の会議ページで「全国銀行協会説明資料（全銀EDIシステムの紹介）」とあり、全銀ネットではなく全銀協。ZEDI の運営は全銀ネット）
  出典: 金融庁「決済高度化官民推進会議」（第 6 回、2019-01-29）資料 4-1 https://www.fsa.go.jp/singi/kessai_kanmin/siryou/20190129/05.pdf （会議ページ https://www.fsa.go.jp/singi/kessai_kanmin/siryou/20190129.html ）
- 同資料: 「企業の多くが複数の商取引の代金を合算して支払い（振込）」し、「受取企業側で認識している回収金額（売掛金）と、実際の入金金額が合わないケースがある。その場合、営業担当や支払企業に照会するなどにより原因を調査する必要がある」と消込の問題を説明している。ZEDI で「さまざまなEDI情報（支払通知番号・請求書番号など）が添付可能」になる。（検証：2026-11-10 確認）
- 同資料の「受取企業の事務負担６割減！」は、出所を「一般財団法人流通システム開発センター 共同実証の結果報告資料（2014年12月）」と注記している（全銀協の説明資料の主張）。（検証：2026-11-10 確認。主体を全銀ネットから全銀協に修正）
- 【自動化の側】全銀ネット https://www.zengin-net.jp/zedi/ を WebFetch で開いた（検証：2026-11-10 確認）。「ZEDI・DI-ZEDI が消込等の自動化を目的とする」と明記した一文は見つからず、Codex の指摘のその言い方は未確認のまま（使わない）。確認できた記述：「売掛金の消込管理にZEDIをご活用いただく場合には、消込に必要なKEY情報を何にするのかなど、添付する金融EDI情報の内容を、予め取引先と相談して決める必要があります。」（よくあるご質問 Q2）。ZEDI とデジタルインボイスの両方に対応した製品を導入すると「請求から決済までの処理を自動化することができます。」（Q7）。記事では「ZEDI は消込に使えるが、KEY 情報を取引先と事前に決める必要がある」の形に限る。DI-ZEDI の項は下にある。
- EDI 情報の量: 全銀固定長形式では 20 桁、XML 形式では 140 桁×最大 500 行。三菱 UFJ 銀行の案内に「全銀固定長形式では20桁であったEDI情報が140桁×最大500行に大幅拡張」。同案内は「XML形式の通知明細データを確認するためには、受取企業も全銀EDIシステムに対応したサービスの利用が必要」と書く。振込データを XML で送る側のサービス（総合振込 XML／総合振込 ZEDI 接続）は注記で「『総合振込』のみご利用いただけます」（給与振込などは対象外の意）。受け取る側の取引通知は「振込入金明細」「入出金明細」が対象で「預金残高」は不可。（検証：2026-11-10 確認。「全銀 XML サービスは総合振込のみ対象」は言い過ぎで、総合振込のみの注記は送信側サービスに付いたもの、と直した）
  出典: 三菱 UFJ 銀行「全銀 XML サービス」（2024-04-15） https://www.bk.mufg.jp/houjin/mufgbiz/info/pdf/20240415_1.pdf
- 同案内の追加料金（消費税込。2024年4月の案内時点の、全銀 VALUX・全銀 ADP サービスのオプションである「全銀 XML サービス」の料金。ZEDI 全般の導入費用ではない）: 全銀 VALUX は契約料金 22,000 円・基本料金 22,000 円、取引通知 XML サービスの従量料金は振込入金明細／入出金明細それぞれ 1 件あたり 5.5 円（データ受信の有無にかかわらず発生した明細件数で課金）。全銀 ADP は契約料金 220,000 円・基本料金 22,000 円。これに加えて全銀 VALUX／ADP サービス本体（総合／給与振込、取引通知）の契約と料金が必要。法人向け（BizSTATION）の有料オプション（記事では、全銀 VALUX・全銀 ADP のオプションの全銀 XML サービスの料金と書く）。（検証：2026-11-10 確認。ADP の基本料金と本体契約が別途必要な点を追記）

  出典: 金融庁「決済高度化官民推進会議」第 8 回 資料 3-1 https://www.fsa.go.jp/singi/kessai_kanmin/siryou/20191223/03.pdf
- DI-ZEDI: 全銀ネットが 2023-04-24 付の案内で制定を発表。デジタルインボイス（JP PINT／JP BIS）と振込の紐づけを容易にし「請求から決済（ZEDI）へのデータ連携による消込処理等の自動化が可能」とする。必須項目は請求書タイプコード（適格請求書 380／仕入明細書 389）、請求書番号（全半角 35 文字以内）、請求書発行日、売手（受注）企業の登録番号。任意項目は請求金額（税込）、買手企業の登録番号、振込手数料負担、備考（140 文字以内）。「総合振込依頼ファイル」の「金融 EDI 情報」欄に設定する。（検証：2026-11-10 確認。必須の「売手企業の登録番号」と任意項目を追記。PDF は IPA のサイトに置かれた全銀ネットの文書）

## 4. バーチャル口座と、それでも残る問題

- ドコモSMTBネット銀行（旧・住信SBIネット銀行。2026年8月3日付で商号変更【確認済み：https://www.netbk.co.jp/contents/company/press/2025/1219_004783.html 】（検証：2026-11-10 オーケストレーター確認））「振込入金専用口座（バーチャル口座）」（記事の出典名もこの名前にする。法人口座の商品で、法人口座開設後に申し込む【確認済み】）: 代表口座に紐づく専用口座番号を請求書ごと・取引先ごとに割り当てる。手数料は無料と記載。作成上限は 1 回 1,000 口座、1 代表口座 1,000 口座。入金は代表口座へ自動で振替され、入出金明細の「内容」欄に「振込専用※（支店番号 3 桁＋口座番号 7 桁＋振込人名の頭 5 文字）」と出る。専用口座宛の振込の一部は、この表示にならない場合がある（原文）。API での確認、過不足・返金の扱いはページに記載なし。対象は「当社所定の支店に口座を開設いただいているお客さま」で、法人口座が前提のページ（/hojin/）。個人事業主が使えるかはページから分からない。同ページの名義違いの例【確認済み】: 請求先の B 合同会社は社長名義、C さまは家族名義で振込。代表口座 1 つで受けると、入出金明細には振込人名が表示されるため、請求情報と振込人名が異なる場合、照合できない（名義違いの説明の出典に使ってよい）。（検証：2026-11-10 確認。法人口座前提の点を追記）
  出典: https://www.netbk.co.jp/contents/hojin/virtual-account/
- Stripe の日本の銀行振込（仮想口座）: 初回に顧客用の仮想銀行口座を作り、その顧客からの以降の振込は同じ口座に来る。「この仮想口座番号が自動消し込みに使用されます」。日本（zengin）では振込参照番号は使われない（reference フィールドは「このフィールドは使用されません」）。口座名義は「ストライプジャパン（カ　シュウノウダイコウ」などの収納代行名義。（検証：2026-11-10 確認。「仮想口座番号が自動消し込みに使用されます」は bank-transfers ページ、reference「このフィールドは使用されません」と zengin の例は accept-a-payment の direct-api 版 https://docs.stripe.com/payments/bank-transfers/accept-a-payment.md?payment-ui=direct-api ）
  出典: https://docs.stripe.com/payments/bank-transfers と https://docs.stripe.com/payments/bank-transfers/accept-a-payment （日本語版、2026-11-10 確認）
- Stripe の過不足の扱い: 不足は「未払いの Payment Intent に部分的に資金を充当」するが「請求書に部分的に資金が充当されることはありません」（請求書は全額入るまで未払い）。過払いは「未払いの決済に対して入金された資金の照合を試行し、残りの超過額を顧客の残高に保持」。（検証：要注意 accept-a-payment の文言は 2026-11-10 確認。ただし reconciliation ページには「請求書の場合、部分支払いの自動消し込みが有効になっており、顧客が振込メモに請求書番号を含めている場合にのみ、入金された銀行振込が部分支払いとして充当されます」と、請求書の確定時に「設定された過少支払いのしきい値」を考慮する旨の記述もあり、「請求書には部分充当されない」は設定次第の例外がある。JPY の自動消込の手順には参照コード照合がないため、日本で請求書への部分充当が起きるかは未確認）
  出典: 同 accept-a-payment ページ「支払い不足と過払いを処理する」、https://docs.stripe.com/payments/customer-balance/reconciliation 「部分支払いと請求書の確定」
- Stripe の JPY の自動消込の順序（日本円では参照番号ではなく、顧客の特定・金額・古さで当てる）:
  【確認済み（delta-1）】顧客ごとの仮想口座で顧客を特定したうえで、顧客の現金残高と金額が一致する 1〜5 件の請求書・PaymentIntent の組み合わせを探す。無ければ、全額を充てられる請求書を確定日時の古い順に、残りを未完了の PaymentIntent に確定日時の古い順に充てる。表やまとめで「なければ古い順に充てる」だけに短縮しない（短縮するなら「決まった順序で充てる（詳しくは本文）」）。「請求書には一部だけ充てられることはない」は設定しだいの例外があるので書かない。（検証：2026-11-10 オーケストレーター確認）（検証：2026-11-10 確認。USD・EUR 等は先に参照コード／請求書番号で照合するが、JPY の手順には参照照合がない）
  出典: https://docs.stripe.com/payments/customer-balance/reconciliation
- Stripe の未消込資金: 「ご自身の責任で、顧客の現金残高が消し込まれていることをスピーディーかつ正確に確認する必要があります」。照合されない資金が 75 日を超えて残ると、顧客の銀行口座への返金を自動で試み（口座閉鎖などで失敗することがある）、90 日を過ぎても残っていれば Stripe の残高に移す（返金の再試行ではない）。Stripe が顧客の口座情報を持っていない場合、顧客に直接「連絡することがあります」。銀行振込による支払いは「USD および CAD での取引を除き、取り消すことはできません」（この「取り消せない」は、購入者の申し立てによる取り消し、カードのチャージバックにあたるものの話で、お店からの返金はできる。同ページは全額・部分返金を認める。返金ができないように読める書き方をしない）。（検証：2026-11-10 確認。「連絡する」を原文どおり「連絡することがある」に。取り消し不可の記述は reconciliation ページではなく bank-transfers ページ https://docs.stripe.com/payments/bank-transfers 。同ページの機能表は不審請求の申し立てを「USD 取引のみ」としており本文と食い違う）
  出典: 同 reconciliation ページ、bank-transfers ページ
- - 【確認済み】Stripe「銀行振込による支払いを返金する」https://docs.stripe.com/payments/customer-balance/refunding : 顧客の残高の支払いはダッシュボードか API で返金できる。返金には顧客の銀行口座の詳細が必要。Stripe が送金のときに口座の詳細を受け取っている場合は、返金の処理を知らせるメールを顧客に送る。口座の情報が使えない・あいまいで特定できない場合は、Customer のメールアドレス宛てに情報をリクエストする。顧客の現金残高への返金（将来の決済に使える）もできる。（検証：2026-11-10 オーケストレーター確認）
- 【確認済み】BASE「銀行振込決済で、支払額を間違えた場合はどうなりますか」（購入者向け）https://help.thebase.in/hc/ja/articles/360000373762 : 不足金は、購入者より BASE 宛に不足金額の振込が必要（専用の振込先を案内するので問い合わせフォームから連絡）。過入金・重複入金は、購入者に差額（重複分）の返金が発生し、BASE からの返金を希望する場合は問い合わせフォームから連絡、返金の手数料は購入者負担。不足金の入金を確認できないと自動キャンセルの対象。例外の扱いはサービスごとに違う（決済サービス全般の一般化はしない）。（検証：2026-11-10 オーケストレーター確認）
